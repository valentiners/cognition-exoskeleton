# 外挂认知模块与记忆模块·完整方案 v3.4

**设计目标**：不动现有已训练模型的源文件与权重，通过在加载程序上外挂「认知模块」与「记忆模块」两个新模块，实现"识别 → 不确定就求助主人 → 共同命名 → 存库 → 复用与纠错"的持续学习闭环。

**版本沿革**：
- v3.1：基础模型已有知识不被重复记忆（三层判定 + 双闸口 + 补丁区）
- v3.2：基础模型更换场景——embedding 与基础模型解耦；补丁审计流程
- v3.3：**换模型零停机**（审计惰性化）；补丁间冲突裁决；REDUNDANT 稳定性测试；补丁出身档案；阈值按模型分桶标定；向量编码器版本校验；遗忘 = 健康度巡检
- v3.4（2026-10-18~19 浏览器实测定型）：交互层改为**拟人化 + 无按钮对话式**；记忆分**临时/永久两层 + 七天法则**；识别流程定为基础模型先认知、LLM 同一性裁决；闸口 2 修订为公共/私人判定；新增特征供给管线。详见第 9 章，凡与上文冲突处以第 9 章为准。

**v3.3 换模型友好承诺（升级）**：
- 更换基础模型时，主条目库零迁移成本（embedding 已解耦）；
- 更换基础模型时**补丁区不再整体挂起**：审计随注入按需发生，系统全程可用；
- 更换外部编码器时，通过向量版本号自动检测并触发一次性重建，无需人工介入。

## 0. 基础模型选型说明（给用户的建议）

| 基础模型类型 | 支持情况 | 体验差异 |
|---|---|---|
| 带视觉识别的多模态模型（推荐） | 完整支持 | 识别快、向主人提问少，特征提取一轮到位 |
| 纯文本 LLM | 支持（保底通道） | 图像识别需多问主人几轮，功能不缺失 |

推荐：优先选用带视觉识别的模型作为基础模型。若条件受限，纯文本 LLM 同样可运行本方案——认知模块的独立性保证了两种情况下识别、命名、存库、复用的完整流程一致，区别仅在特征提取阶段提问的轮数。

**v3.x 范围说明**：本版本支持图像 + 文本两种输入模态。语音输入涉及 ASR 与音色特征提取，复杂度较高，暂不纳入，留待后续版本评估。

## 1. 总体架构

```
图像 ──┐
       ├──→ 特征提取层 ──→ 统一结构化描述 ──┐
文本 ──┘   （感知通道 A / 交互通道 B）       │
                                           │  embedding 由独立外部编码器生成
                                           ▼
                              ┌─────────────────────┐
                              │      认知模块        │
                              │  · 查记忆模块 (≥70%) │
                              │  · 比对原模型知识     │
                              │  · 灰色地带 → 主人仲裁 │
                              │  · 多维度分析 + 共同命名│
                              │  · 防重复判定        │
                              └──────────┬──────────┘
                                         ▼
                              ┌─────────────────────┐
                              │      记忆模块        │
                              │  entries：主条目库   │
                              │  patches：基础模型   │
                              │  知识补丁区(含审计史) │
                              └─────────────────────┘
```

**核心原则**：
- 原模型只被调用，权重与源文件不被修改；
- 认知模块内部不直接处理原始图像/文本，一切输入先转为统一的多维度特征描述；
- embedding 与基础模型解耦：向量由独立外部编码器生成，更换基础模型不影响记忆库检索能力；
- 一切状态变更只追加、不覆盖，保留完整演化轨迹；
- **单主人原则（v3.3 明确）**：系统按唯一主人设计，主人身份即最高权限与唯一可信输入源，全文所述"主人仲裁/主人批准"均指向同一身份；不预留多主人/多角色的作用域与权限层——若未来出现此需求，属架构级变更，不在本方案演进范围内。

## 2. 识别流程与阈值机制

### 2.1 两级阈值 + 仲裁区

| 阶段 | 比对对象 | 相似度 | 动作 |
|---|---|---|---|
| 第一次遇到 | 原模型压缩知识 | > 51% | 猜测性回答（疑问句"是……吗？"），等主人确认 |
| 第一次遇到 | 原模型压缩知识 | ≤ 51% | 承认未知，询问主人 |
| 之后遇到 | 记忆模块主条目 | ≥ 70% | 确认命中，输出识别结果 |
| 之后遇到 | 记忆模块主条目 | 51% ~ 70% | 灰色地带 → 主人仲裁（不自动下结论） |

> **v3.4 修订（实测定型，见 §9.3）**：上表阈值按编码器标定后实际取值为 **mem_th=0.78 / base_th=0.51**（标定依据 §9.6）；且"灰色地带 → 主人仲裁"不再是第一选择——**先由基础模型做同一性裁决（judge_same），它拿不准才升级给主人**。运行顺序以 §9.3 为准。

### 2.2 完整流程图

> **v3.4 注**：本图是 v3.3 概念流程；实测定型的执行版见 §9.3（基础模型先认知、DIRECT 直通、LLM 同一性裁决优先于主人仲裁）。

```
新输入 → 特征提取层 → 统一描述（覆盖率检查，见 2.3）
                    │
                    ▼
        查记忆模块 entries（外部编码器向量检索）
                    │
        ├─ ≥70% ────────────────→ 确认命中，输出识别结果
        │
        ├─ 51%~70%（灰色地带）──→ 问主人："这像不像之前认识的「X」？"
        │    ├─ "是"   → MERGE：追加更新旧条目
        │    ├─ "不是" → NEW：走新建流程
        │    └─ "是 X 的幼体" → SUBCLASS：新建子类条目
        │
        └─ <51% ────────────────→ 比对原模型压缩知识
             ├─ >51% → 猜测性回答 ──闸口 1（第 4.2 节）
             └─ ≤51% → 承认未知 → 命名流程
                          → 防重复判定 → 入库或存补丁
```

### 2.3 特征覆盖率前置检查

任何输入经特征提取层后，若维度覆盖率过低（如 < 40%），不进入猜测/未知分支，直接走交互通道向主人补问特征，直到覆盖率达标。比对时只对双方都存在的维度计算相似度并报告覆盖率；覆盖率过低即使相似度达标也应触发仲裁（防假命中）。

> v3.3 注：覆盖率阈值与相似度阈值一样属于需要标定的参数，纳入 5.3 的分阶段标定流程，不硬编码。

## 3. 特征提取层（多模态设计）

### 3.1 两条通道

- **通道 A：感知通道**（基础模型带视觉识别时，推荐）
  图像 → 原模型视觉能力 / 独立视觉编码器 → 直接输出结构化特征
- **通道 B：交互式通道**（纯文本 LLM 保底）
  图像 → 传统 CV 低层工具（颜色直方图、边缘检测、尺寸比例）→ 不足以识别 → 认知模块主动向主人有目标地补问

### 3.2 embedding 解耦原则

```
统一描述 →【独立外部编码器】→ 向量 → 存库 / 检索
              ↑
   与基础模型无关，可单独选型与更换
```

- 外部编码器负责所有入库与查询向量的生成，基础模型不参与向量空间；
- 更换基础模型时无需重新 embedding 全库；
- 若未来更换外部编码器本身，需要全库重嵌入一次（一次性离线任务）。

### 3.3 v3.3 向量版本校验（新增）

- 每条 entry / patch 的向量元数据中记录 `embedding_model` 版本号（如 `"embedding_model": "bge-m3@2026.06"`）；
- 检索加载时逐批校验向量版本：发现与当前编码器不匹配，即触发**一次性离线重建任务**，为相关条目重新生成向量；
- 原始文本永远是一等公民，向量只是可重建的缓存——任何编码器切换都是"检测 → 重建 → 留痕"的同一套机制，无需人工判断；
- 重建任务写入条目的 `updates` 留痕（只追加原则）。

### 3.4 跨模态一致性要求

- 文本解析器把自然语言描述拆成维度键值对（由基础模型完成）；
- 维度归一化：视觉输出"约 40cm"与文本"个头不小"归到同一尺度；
- 缺失维度处理：只对双方都存在的维度算相似度并报告覆盖率。

## 4. 防重复记忆机制

### 4.1 三层判定：什么该进库

| 情况 | 例子 | 处理方式 |
|---|---|---|
| 完全已知的常识 | 猫、狗、汽车 | 绝不建条目，流程结束 |
| 知道但细节超出其粒度 | 知道"橘猫"，说不出"这只尾巴是弯钩形" | 存增量补丁，不建主条目 |
| 认识但本次识别错误/拒识 | 知道"缅因猫"但认错了 | 存纠错补丁，不建主条目 |
| 完全未知（私人知识/专名） | "豆豆" | 建完整主条目 |

**主规则**：事务能被基础模型压缩知识完整覆盖 → 不建条目。**例外**：认识但粒度不够 → 增量 patch；识别错误 → 纠错 patch。**兜底原则**：基础模型词汇表已有的通名默认不进库；主人赋予的专名默认建条目。

### 4.2 双闸口 + 建库前去重

**闸口 1：GUESS 分支确认回环**

```
猜测 → 主人确认 → 回环提问：
"这就是普通的猫，对吗？还是有特别之处你想让我记住的？"
├─ "就是普通的猫"     → 丢弃，不入库
├─ "尾巴是弯钩形的"   → 存 patch
└─ "是我家的豆豆"     → 专名 → 闸口 3 → 建主条目
```

**闸口 2：命名环节专名/通名自检**

> **v3.4 修订（实测踩坑后定型）**：自检问题从"基础模型能否零样本给出完整、稳定描述"（`is_common_knowledge`）改为**"该事物是公共知识还是私人事物"**（`is_public_knowledge`，结合上下文判断）。原因：常见人名/通名（如"小黄""Lucy"）会被旧探测误判为公共知识——基础模型"认识这个词"不等于"这是公共概念"。实测案例：三条腿流浪猫命名"小黄"时被旧闸口误判，存成了补丁而非主条目。新探测模型拿不准时默认信任主人的教学（判私人），交由闸口 3 查重兜底。

`is_common_knowledge(name)`：基础模型能否零样本给出完整、稳定描述。True（通名）→ 只存 patch；False（专名）→ 闸口 3。（v3.4 起以 `is_public_knowledge` 为准，本行保留仅为历史对照。）

**闸口 3：建库前去重**

- 与某主条目特征相似度 > 70% → 阻断，走 MERGE；
- 与某补丁 target 概念重合 → 合并进该 patch。

### 4.3 补丁区结构（patches）

```json
{
  "id": "P-0001",
  "target": "猫",
  "target_origin_base": "model-v1",
  "type": "feature_addition",
  "content": { "尾巴形状": "蓬松弯钩" },
  "source_entry": "M-0001",
  "priority": 0,
  "status": "active",
  "audit_history": [
    {
      "audited_at": "...",
      "base_model_version": "model-v2",
      "verdict": "STILL_VALID",
      "note": "..."
    }
  ],
  "created_at": "...",
  "updates": []
}
```

**v3.3 新增字段说明**：
- `target_origin_base`：补丁出身模型——针对哪个基础模型的哪个版本写成。审计分级信任与家族内跳审的依据（见 4.5.4）；
- `priority`：补丁间冲突裁决优先级，数值大者优先（见 4.5.6）。

**补丁区使用规则**：
- 不参与首轮向量检索：新输入首轮比对靠基础模型自身 + 主条目库；
- 仅当基础模型识别命中后作为增强/纠偏层被调用；
- `status != "active"` 的补丁不参与纠偏调用：`archived`（已冗余归档）、`suspended`（冲突挂起，待主人裁决）；
- 同一 target 下多条补丁同时命中时，按 4.5.6 的裁决规则择一或合并生效。

### 4.4 入库决策总表

```
待入库状态：
├─ 基础模型能完整覆盖？── 是 ──→ 丢弃
├─ 认识但需增补/纠错？── 是 ──→ 存 patch
├─ 专名/私人知识？
│    → 与 entries 条目 >70%？── 是 ──→ MERGE
│    → 与 patches target 重合？── 是 ──→ 合并进 patch
│    → 均否 ──→ 新建主条目
└─ 灰色仲裁结果 → MERGE / NEW / SUBCLASS 分流
```

### 4.5 v3.3 补丁审计流程（基础模型更换场景）

> v3.3 核心变化：由 v3.2 的"全量前置审计 + 整体挂起"改为**惰性按需审计 + 轻量前置摸底**，换模型后系统全程可用。

#### 4.5.1 触发（v3.3 修订）

- 检测到基础模型 ID/版本变化 → 触发**前置摸底**（仅覆盖测试，见下），同时标记所有补丁的审计缓存失效；
- **不再挂起补丁区**：补丁是否可用，由"该补丁在当前模型下的审计结论"逐条决定，而非全局开关；
- 支持手动触发（如怀疑补丁与新模型不合时）。

**前置摸底（轻量）**：新模型对补丁区涉及的所有 target 概念批量跑一次覆盖测试，分钟级完成，产出一张"概念 → 认识/不认识"总表。作用有二：
1. 让系统立刻知道哪些补丁大概率失效（ORPHAN 候选），在注入时优先处理；
2. 为 5.3 阈值按模型分桶重标定提供输入。

#### 4.5.2 注入时按需审计（v3.3 新增，替代全量审计）

- 一条补丁在**首次被准备注入**时，才对它跑完整三类探测（4.5.3）；
- 审计结果缓存：该补丁在当前模型版本下后续命中直接复用结论，不重复探测；
- 从不被检索到的补丁永远不花审计成本——审计开销均摊到正常使用中；
- 兜底：摸底表中标为"不认识概念"的补丁，注入时直接走 ORPHAN 分支，跳过探测 2、3。

#### 4.5.3 三类探测（新模型对每条待审计 patch）

| 探测 | 内容 |
|---|---|
| 探测 1 覆盖测试 | 新模型认识 patch.target 概念吗？ |
| 探测 2 一致性测试 | 新模型对该概念的描述中，已包含 patch.content 的特征吗？（多次采样取一致性） |
| 探测 3 冲突测试 | 新模型的描述与 patch.content 明确矛盾吗？ |

**减负设计**：按 target 分组批量探测——同一概念下的多条补丁共享概念探测与综合描述，成本从 O(补丁数) 降到 O(概念数)。

**v3.3 新增——REDUNDANT 扰动稳定性测试**：

新模型对自身知识的描述存在**自评偏差**风险（自信地声称知道其实不可靠掌握的细节）。因此凡探测 2 初判为"已包含该特征"（候选 REDUNDANT）的补丁，归档前必须通过扰动稳定性测试：

- 对该知识点做改述、反事实追问、换提问角度等多路探测；
- 全部一致维持"已包含"结论 → 判 REDUNDANT，归档；
- 任一路出现摇摆或前后矛盾 → 降级为 STILL_VALID，补丁继续生效。

成本只花在少量候选归档补丁上。

#### 4.5.4 四分类处置

| 探测结果 | verdict | 处置 |
|---|---|---|
| 不认识概念 | ORPHAN | 新模型能力差异大 → 补丁升级为主条目候选，走主人确认 |
| 认识、无此特征、无矛盾 | STILL_VALID | 保留 active，继续生效 |
| 认识、已包含该特征 | REDUNDANT | 归档（status=archived，留痕不硬删）——防重复原则在换模型场景的延伸 |
| 认识、但描述矛盾 | CONFLICTING | 挂起（status=suspended），不自动处置，标记待主人仲裁："新模型认为是 X，旧补丁说是 Y，听谁的？" |

#### 4.5.5 原则

- 审计结果只追加不覆盖：全部写入 audit_history；
- CONFLICTING 补丁主人裁决前不参与纠偏；
- **分级信任（v3.3 做实）**：
  - 上次判 STILL_VALID 的补丁，下次换模型降频复审；
  - 上次审计所针对的模型与本次新模型**同家族且为 minor 升级**（由 `target_origin_base` 与 `audit_history.base_model_version` 判定）→ 整批跳过或只做覆盖测试；
  - REDUNDANT 归档区与 CONFLICTING 挂起区每次全量重审。

#### 4.5.6 补丁间冲突裁决（v3.3 新增）

v3.2 的审计只处理"补丁 vs 新模型"，未处理"补丁 vs 补丁"。同一 target 下多条补丁内容矛盾时，注入按以下规则裁决：

1. **target 精确度高者优先**（指向子概念的补丁优先于指向父概念的补丁）；
2. **priority 字段大者优先**（主人可手动调整，用于显式指定"以这条为准"）；
3. **创建时间新者优先**（后写入的补丁视为对前序的修正）；
4. 检测到无法裁决的互相矛盾（如两条同优先级补丁内容直接冲突）→ 一并进入主人仲裁队列，复用 `resolve_conflict` 接口，与 CONFLICTING 处置共用一个裁决入口。

裁决结果写入相关补丁的 `updates` 留痕。

## 5. 记忆模块

### 5.1 主条目结构

```json
{
  "id": "M-0001",
  "name": "橘色短毛猫",
  "features": {
    "shape": "...", "size": "约 40cm", "color": "橘色",
    "age": "成年", "category": "猫科/家养宠物",
    "embedding": [0.12, -0.33, "..."]
  },
  "embedding_meta": { "model": "bge-m3@2026.06" },
  "provenance": {
    "source_modality": "image",
    "extraction_channel": "A",
```

**v3.3 新增/调整**：
- `embedding_meta.model`：向量编码器版本号，供 3.3 的加载校验使用；
- `threshold_meta.by_base_model`：阈值统计按基础模型版本分桶——51% 闸口比对的是"原模型压缩知识"，换模型后语义即漂移，分桶记录使每套阈值都可追溯、可独立重标定；
- `health`：条目健康度，遗忘巡检（6.3）的输入。

### 5.2 核心原则

1. 只追加、不覆盖；
2. 错误事件单独成档，保留认知演化轨迹；
3. 持久化：JSON + 向量索引，无需数据库；
4. 随时可检索；
5. 不重复记忆基础模型已有知识，入库前必须通过第 4 节判定与闸口；
6. 更换基础模型时主条目库零迁移成本（embedding 已解耦）；
7. **v3.3**：更换基础模型后，阈值统计按新模型分桶重新累积，旧桶数据保留供对比。

### 5.3 阈值标定流程（数据驱动，v3.3 修订）

> **v3.4 注**：本节是方法论。primitive version 已按当前编码器（embeddinggemma-2）完成一轮标定，实际运行值见 §9.6（mem_th=0.78、base_th=0.51、临时记忆 0.62）；本节"45% / 65%"等保守值是概念阶段的示例起点，非当前配置。换基础模型/编码器时按本节流程重新标定并更新 §9.6。

**阶段一（冷启动）**：保守值（45% / 65%），宁可多问不可乱认。每个基础模型版本第一次接入都从此阶段开始。

**阶段二（50+ 条交互后）**：画「相似度-正确性」分布图，谷底定阈值。

**阶段三（运行期）**：
- 每识别必写 `threshold_meta`（按当前 `base_model_version` 分桶）；
- 单条目错误率 > 30% → 自动降权或强制仲裁；
- 换基础模型 → 新模型桶自动回到阶段一保守值，同时跑一次 4.5.1 的轻量摸底辅助快速标定；
- 阈值可调，调整留痕。

## 6. 维度治理与遗忘机制

### 6.1 维度治理（防维度爆炸）

```json
DIMENSION_REGISTRY = {
  "标准维度": ["形状", "尺寸", "颜色", "年龄", "类型"],
  "别名表": { "大小": "尺寸", "体型": "尺寸", "种类": "类型" },
  "维度上限": 20,
  "合并策略": "维度名语义相似度 > 0.85 自动合并，冲突值以主人为准"
}
```

1. 新维度先查别名表归一化；
2. 仍不存在的向主人报告并需主人批准加入；
3. 达上限按区分贡献度末位淘汰，淘汰记录进 `updates` 留痕。

### 6.2 维度治理与条目治理共用淘汰思想

维度层已有"区分贡献度末位淘汰"的机制。v3.3 将同一思想复用到条目层，形成统一的**健康度巡检**框架（6.3），遗忘不再是换模型时的一次性事件，而是常态化背景任务。

### 6.3 v3.3 遗忘 = 健康度巡检（新增）

**健康度指标**（每条 entry / patch 的 `health` 字段）：

| 指标 | 来源 | 意义 |
|---|---|---|
| `last_hit_at` / `hit_count` | 检索日志 | 长期无人问津的内容是休眠候选 |
| `error_rate` | `threshold_meta` | 高错误率的条目在干扰检索，应降权或强制仲裁 |
| `audit_verdict` | 补丁审计 | STILL_VALID 之外的状态影响存活策略 |

**巡检规则**：
1. 健康度低于阈值 → 进**遗忘候选队列**（休眠而非删除，原始数据保留）；
2. 队列由主人定期确认：保留 / 归档 / 彻底删除；
3. 也可配置策略自动休眠（如：连续 90 天零命中且错误率 > 30% → 自动休眠，主人可一键唤回）；
4. 休眠条目不参与检索，但保留全部历史与 `updates`，唤回零成本。

**回流任务的常态化**：遗留问题中的"外挂知识向模型能力的回流"，在 v3.3 中落实为巡检的一个定期子任务——按 target 分组探测当前基础模型，评估哪些补丁/主条目内容已被模型完整吸收（即 REDUNDANT 判定的常态化运行），被吸收者归档留痕。

## 9. v3.4 增补：浏览器实测迭代定型（2026-10-18 ~ 10-19）

> v3.4 不是推翻 v3.3，而是 v3.3 机制经最小可运行版本（Ollama + 本地 HTTP 服务 + 浏览器 UI）**实测后的定型修订**。凡本节与上文冲突之处，以本节为准。本章同时是正式开发的交接依据（代码 agent 以本章 + AGENTS.md 为准）。

### 9.1 交互层定型：拟人化 + 无按钮对话式（新增原则）

实测后否决了"按钮式仲裁"——每次弹按钮都是对主人的打扰，且不像生命体。定型规则：

1. **废除一切按钮式强制选择**；一切判断通过对话本身完成（按钮只允许作为可选便利保留，不得是唯一通道）；
2. **对话意图分类** `classify_followup(context, utterance)`：话题上下文中主人的每句话，由基础模型一次调用分类为 `feature`（补充信息，输出"属性: 内容"）/ `remember` / `forget` / `none`；关键词正则仅作 LLM 调用失败时的兜底；
3. **一切未决流程的自由文本都是回答**（arbitrate / guess / gate1 / naming 等），带模糊理解："不是/不对/没"→否，"是/对/嗯/好"→是，"算了/取消"→取消整个流程；听不懂就自然追问，不猜；
4. **话题 30 分钟冷却**：超时未续自动作废（鲜活生命体不无限盯着旧话题）——**仲裁类挂起的超时处置见 §9.11：不是丢弃，是降级暂存**；
5. **全部回复拟人、口语、第一人称**；机械标注（action=xxx、置信度、命中路径）只出现在 debug 字段，不进主文案。
6. **机制自我表述也不进聊天文案**（2026-10-20 定型）："就不占用我的长期记忆啦""我悄悄记下了"这类对外解释内部记忆机制的句子，属于思考过程，只允许留在 debug 字段；聊天窗口里只说自然对话本身（"哦，他叫小明呀，我记下了"）。主人要的是鲜活生命体，不是会自言自语报告自己工作原理的机器。

### 9.2 记忆分层：临时记忆与七天法则（对第 5 节的增补）

主人 2026-10-19 定型，**替代了此前过渡版的"特征缓存后弹按钮问主人是否入库"**：

1. 所有新事物的特征**一律先暂存临时记忆**（独立 JSON 文件，与永久记忆平级，同样只追加、git 不入库）；
2. 主人对话里说"记住它"（"remember it"亦可）→ **立即晋升**永久记忆，仍走闸口 2/3；
3. 主人没说 → 留在临时记忆，**滚动保留 7 个自然日**，超期自动遗忘；
4. **同一事物 7 天内在不同日期出现 ≥3 次 → 自动晋升**永久记忆，并在对话中自然告知（"它这几天老是出现，我就把它正式记住了"）；
5. 晋升时缺名字 → 对话式追问（"那我该怎么称呼它？"），主人自由文本即回答。

**适用范围界定**：临时记忆管的是**对话中自然涌现的特征供给**（§9.4 管线）。闸口 1 教学回环（§4.2）中主人明确说"叫 X"或给特征描述的场景，属于**主人已有明确入库意图**，维持原流程直接入库/存补丁，不再绕临时记忆——避免为已经明确的事再添一跳。

实现要点：
- 窗口滑动：cutoff = 今天 − 6 天，最早一次出现会滑出窗口，不会"陈年凑数"；同一天内重复出现只记一个日期；
- 临时记忆命中阈值 0.62（同编码器，低于永久记忆 0.78 的宽松档）；
- 与 6.3 健康度巡检的分工：七天法则是"还没进永久库"的快速遗忘；健康度巡检是永久库的长期治理。两者互补，不冲突。

### 9.3 识别流程实测修正（修订 §2.1 / §2.2）

实测定型的运行顺序（§2.2 流程图的执行版）：

1. 永久记忆 ≥ mem_th(0.78) 命中 → RECOGNIZED——**但个体条目（`provenance.source_modality == "image"` 的专名，如 Lucy/豆豆）必须再过同一性复核**：`judge_same` 判"是"才认出，判"否"落到下方基础模型认知（同类直通/未知），拿不准 → GUESS 问主人。原因：向量命中只证明"像这个类别"，不能证明"是同一个人"；实测中形象完全不同的女孩照因入库描述太泛（类别级）被 0.84 误命中。此复核即设计文档 §2.3"特征覆盖率不足防假命中"的执行版。
2. **基础模型先判断**（infer + infer_confidence）：
   - 它认识的类别下恰好一个专名 → `judge_same` 同一性裁决：**是** → 认出；**否** → 落入未知/命名；**拿不准** → GUESS 问主人；
   - 类别下多个专名候选 → GUESS；
   - 与任何专名无关 → **DIRECT 常识直通，不弹窗、不打扰主人**；
3. 基础模型也不确定 → 向量近邻（≥0.5）+ `judge_same` 兜底裁决；
4. 全不成立 → UNKNOWN → 命名教学流程。

**核心教训**：v3.3"灰色地带事事问主人"在实测中被否决。灰色地带应先由基础模型自己裁决（LLM 同一性判断），它真拿不准才升级给主人——**每一次弹窗都是对主人的打扰**。

闸口 2 的修订见 §4.2（v3.4 注）。

### 9.4 特征供给管线（主人主动喂特征，新增流程）

主人随时可用一句话给当前话题的事物补充信息（"她叫 Lucy""它今年三岁"），处理管线：

```
主人补充信息 → 意图分类为 feature → 特征暂存临时记忆（无追问、无确认）
     → 拟人应答（"哦，她叫 Lucy 呀，我记下了"——只留自然对话，机制说明见 §9.1 第 6 条）
     → 后续由"记住它"（立即晋升）或七天法则（自动晋升）落永久库
```

**旧版误判实录（教训）**：早期实现把 "the girl's name is Lucy" 当成全新陌生事物走 UNKNOWN 命名流程，导致条目描述被污染（混入 "what is this?" 问句与模型寒暄前奏）。**特征供给的判定必须先于"新事物判定"**——上下文里已有话题时，先判意图，再谈识别。

### 9.5 感知与问答通道实测补充（修订 §3.1）

- **图像回复格式定型**：先声明"我看到一张图片——"再给出描述，然后才说认不认识；
- **身份级描述提示词（v3.4 定型）**：看图提示词必须要求"抓住能把这个个体与同类其他个体区分开的细节"（人物：发型发色/瞳色/脸型/服装配色/配饰/显著标记；动物：毛色花纹/耳尾眼形态；物品：材质/磨损/独特处），先一句话说类别再罗列区分性细节——类别级描述（"一位穿粉黑服装的女性角色"）对同类所有个体都通用，是个体误认的根源（实测：两张形象不同的女孩照都被认成 Lucy）；
- 视觉提示词必须加"只输出描述本身，不要寒暄或解释"——实测 gemma4 会带"好的，请看…"前奏，污染入库 embedding；输出端再剥一遍 markdown 装饰符（**/ # /列表符）双保险；
- 纯问题（无图且命中问句特征"是什么/为什么/吗/?"等）→ `answer_question` 直通，不进记忆流程（v3.3 主规则 4.1 的执行版）。
- **指代问题必须带话题上下文**（2026-10-20 定型）：主人发图后追问"他是谁？""她叫什么？"时，`answer_question` 必须把当前话题上下文（已识别对象的名字、已暂存特征）拼进提问，否则模型会把指代当悬空引用、反向索要上下文（"请提供您想让我识别的'他'的上下文信息……"），聊天当场断裂。同理：看图时若附带文字本身是纯问句，该文字不得作为 hint 传给 `perceive_image`（否则描述被问句污染）；临时记忆命中图像个体时也要过 `judge_same` 同一性复核，复核不通过按新事物继续走，不得直接应答。

### 9.10 记忆休眠机制与分层检索（主人 2026-10-20 定型，修订 §5 / §6.3）

记忆库增长后的检索效率与长期治理：**长期不被调用的记忆转入休眠，日常检索不纳入；主人追问"再想想"时才翻休眠层**。

**休眠判定（派生态，不增设存储结构）**：

- 条目 `last_hit_at`（health 字段，原本就是 §6.3 遗忘巡检的数据源）距今超过 **365 天** → 休眠；从未被命中过的条目以 `formation.created_at` 起算；
- 休眠是**查询时派生**的判定，不写状态位、不搬库存储——命中即 `touch`，`last_hit_at` 刷新，条目自然复活。休眠 ≠ 删除，与"只追加"铁律无冲突；
- 依赖修复：`touch` 原本只改内存不落盘，重启后命中记录全丢、休眠永远判定不出来——已补持久化。

**分层检索（三层，同一编码器同一 mem_th）**：

| 层 | 范围 | 触发时机 |
|---|---|---|
| L1 高频层 | 非休眠 且 近 90 天有命中（不设次数门槛） | 每次日常检索先查 |
| L2 活跃层 | 全部非休眠条目 | L1 无命中时**静默扩检**（不打扰主人） |
| L3 休眠层 | 休眠条目 | **仅**主人说"再想想/好好想想/仔细想想/你忘了吗/你忘了"时 |

- 高频 = 近 90 天有命中即算，**不设次数门槛**（2026-10-20 修订）：命中一次就说明主人近期还在提它；次数权重留给未来的检索排序优化，分层过滤只管"近期是否活着"；
- L2 的存在保证低频但活跃的记忆不失效——分层管的是**检索顺序与休眠排除**，不是把低频记忆踢出日常；
- L3 由 `cognition.recall()` 专属入口执行，只做记忆向量检索（不走基础模型认知——基础模型第一遍已经答过，答不出才轮到翻旧账）；命中后走正常同一性复核（图像个体同样过 `judge_same`），应答"啊……我想起来了，是 X！"；
- 未命中 L3 → 自然应答"翻遍了记忆的角落也没有印象"，未决的教学流程保持原状不取消；
- **触发词判定必须挂在问答直通之前**——"你忘了吗"含"吗"字，会被问句特征规则（QA_PATTERN）截胡成常识问答（实测教训同 §9.5 指代问题）；
- `best_match`（闸口 3 查重、灰色地带仲裁）**不受休眠限制**，保留全库——查重是为了防重复建库，不能因为条目睡着了就允许主人给它起第二个名字。

**与七天法则的分工**：临时记忆的 7 天滚动遗忘管"还没进永久库"的快速淘汰；休眠管永久库的长期治理（§6.3 健康度巡检的具体实现）。两者互补，不冲突。

### 9.11 仲裁超时降级（主人 2026-10-20 定型，修订 §9.1 第 4 条）

仲裁异步化采用**降级**路线：超时未获主人答复的挂起项，**静默降级写入临时记忆**，不打扰主人当前的工作。理由（主人原话）：临时记忆有 7 天有效期，主人想起来了再聊同样的话题，机制自然唤醒；七天内都不再提，说明不重要，也没有永久记忆的必要。

**触发**：仲裁类 pending（naming / guess / gate1 / arbitrate）超过 30 分钟未获答复，主人下一条消息到达时判定。

**动作**：
- 有可暂存内容（挂起时缓存的 text/描述）→ `temp.add` 静默暂存，仅 debug 留痕，不在聊天窗口声张；
- 暂存前查临时记忆近似项（≥0.62 视为同一件事的已在册记录），防同一件事超时反复挂起导致重复暂存；
- 无可暂存内容 → 丢弃，debug 留痕；
- **主人明确说"算了/取消" → 真丢弃，不降级**——降级只用于"没来得及答"，主人的明确意图永远优先；
- **铁律：降级永不写永久库、永不做 MERGE**——MERGE 会重算 embedding、不可逆，自动决策永远偏向"不合并、只暂存"。

**超时后主人又答了**：超过 30 分钟的答复不再路由进原挂起流程（已降级），按新输入正常处理。

**唤醒与遗忘全部复用现有机制，零新增**：
- 主人再提起 → 临时记忆命中（TEMP_HIT）自然应答；补充名字走特征供给管线（§9.4），"记住它"立即晋升；
- 七天内 ≥3 个不同日期出现 → 七天法则自动晋升永久（§9.2）；
- 七天不再提 → 滚动遗忘（§9.2）= "不重要，无需永久记忆"。

**不适用降级的情况**：promote_name（追问名字）挂起期间，其临时记录本来就留在临时记忆里，超时无需任何动作；promote_name 到期后若临时记录也被七天法则遗忘，视为整体放弃。
