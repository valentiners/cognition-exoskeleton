# 外挂认知模块与记忆模块·完整方案 v4.0 / Cognitive & Memory Exoskeleton — Full Design v4.0

> 本文档中英双语：每个章节先中文、后英文，内容一一对应。
> Bilingual document: each chapter appears first in Chinese, then in English, with one-to-one correspondence.

**设计目标 / Design Goal**：不动现有已训练模型的源文件与权重，通过在加载程序上外挂「认知模块」与「记忆模块」两个新模块，实现"识别 → 不确定就求助主人 → 共同命名 → 存库 → 复用与纠错"的持续学习闭环。
Without touching the source files or weights of any already-trained model, attach a "Cognitive Module" and a "Memory Module" on top of the loader to achieve a continuous-learning loop: **perceive → ask the master only when unsure → name together → store → reuse & self-correct**.

**版本沿革 / Version History**：
- v3.1：基础模型已有知识不被重复记忆（三层判定 + 双闸口 + 补丁区）/ No duplicate memory of what the base model already knows (three-layer test + two gates + patch zone)
- v3.2：基础模型更换场景——embedding 与基础模型解耦；补丁审计流程 / Base-model swap scenario — embedding decoupled from the base model; patch audit flow
- v3.3：换模型零停机（审计惰性化）；补丁间冲突裁决；REDUNDANT 稳定性测试；补丁出身档案；阈值按模型分桶标定；向量编码器版本校验；遗忘 = 健康度巡检 / Zero-downtime model swap (lazy audit); inter-patch conflict arbitration; REDUNDANT perturbation test; patch origin records; per-model threshold calibration; embedding-version check; forgetting = health sweep
- v3.4（2026-10-18~19 浏览器实测定型）：交互层改为拟人化 + 无按钮对话式；记忆分临时/永久两层 + 七天法则；识别流程定为基础模型先认知、LLM 同一性裁决；闸口 2 修订为公共/私人判定；新增特征供给管线 / Browser-tested finalization: humanized button-free conversational interaction; two-layer (temp/permanent) memory with the 7-day rule; base-model-first perception with LLM identity judgment; gate 2 revised to public/private test; feature-supply pipeline

## 0. 缘起 / Why This Exists

**中文**

如果住在自己电脑里的模型伙伴能像人一样认识世界——自己注意到新事物，记住生活里的点点滴滴，像一个真正的伙伴一样陪着你成长，会怎样？

完全重新训练一个模型又慢、又复杂、又贵。所以我一直在问：能不能用一个简单的外挂，就给任意一个已训练好的模型赋予对新事物的基础认知和自我学习能力——不重训，不动权重？

这个问题催生了本项目：**自认知进化**（cognitive evolution）。
（让本地模型伙伴像人一样认知、记忆、陪伴——不靠重训，靠外挂。By Ricky Li, github.com/valentiners）

**English**

What if the model living on your own computer could learn about the world the way we do — noticing new things on its own, remembering the small moments of your daily life, growing alongside you like a real companion?

Retraining a model from scratch is slow, complex, and expensive. So I kept asking myself: could a simple exoskeleton give *any* already-trained model basic cognition and self-learning — no retraining, no weights touched?

That question became this project: **Cognitive Evolution (自认知进化)** — so a local model partner can perceive, remember, and accompany like a human: not by retraining, but by an exoskeleton. (By Ricky Li, github.com/valentiners)

## 1. 总体架构与核心原则 / Overall Architecture & Core Principles

**中文**

```
图像 ──┐
       ├──→ 特征提取层 ──→ 统一结构化描述 ──┐
文本 ──┘   （感知通道 A / 交互通道 B）       │
       ┌─────────────────────────────────────┴───┐
       │              认知模块（Cognitive Module）│
       │  · 分层检索记忆模块（高频/活跃/休眠，§6.4）│
       │  · 比对基础模型认知（先让基础模型判断）    │
       │  · 同一性裁决 judge_same → 灰色地带才问主人│
       │  · 多维度特征分析 + 共同命名              │
       │  · 三道闸口防重复（§5）                   │
       └──────────────────┬──────────────────────┘
                          ▼
       ┌──────────────────────────────────────────┐
       │              记忆模块（Memory Module）    │
       │  entries：永久主条目库                   │
       │  temp：临时记忆（七天法则，§6.3）        │
       │  patches：基础模型知识补丁区（含审计史） │
       └──────────────────────────────────────────┘
```

**核心原则（铁律，全文有效）**：
1. 原模型只被调用，权重与源文件不被修改；
2. 认知模块内部不直接处理原始图像/文本/视频，一切输入先转为统一的多维度特征描述；
3. embedding 与基础模型解耦：向量由独立外部编码器生成，更换基础模型不影响记忆库检索；
4. 一切状态变更只追加、不覆盖，保留完整演化轨迹；
5. **单主人原则**：系统按唯一主人设计，主人身份即最高权限与唯一可信输入源；全文"主人仲裁/主人批准"均指向同一身份；不预留多主人/多角色的作用域与权限层——若未来出现此需求，属架构级变更，不在本方案演进范围内；
6. **全拟人化交互**：对主人的一切回复口语、第一人称、像鲜活生命体；机械标注（action、置信度、命中路径、记忆机制自我说明）只出现在 debug 字段，不进聊天文案（§4.1）。

**English**

```
image ──┐
        ├──→ feature extraction ──→ unified structured description ──┐
text ──┘   (perception channel A / interaction channel B)            │
        ┌─────────────────────────────────────────────────────────┴──┐
        │              Cognitive Module                                │
        │  · layered memory retrieval (frequent/active/dormant, §6.4)  │
        │  · compare with base-model cognition (base model judges first)│
        │  · judge_same identity judgment → master only in gray zone   │
        │  · multi-dimensional feature analysis + co-naming            │
        │  · three anti-duplication gates (§5)                         │
        └─────────────────────┬────────────────────────────────────────┘
                              ▼
        ┌──────────────────────────────────────────────────────────┐
        │              Memory Module                               │
        │  entries: permanent main-entry store                     │
        │  temp: temporary memory (7-day rule, §6.3)               │
        │  patches: base-model knowledge patch zone (with audit)   │
        └──────────────────────────────────────────────────────────┘
```

**Core principles (hard rules, valid throughout)**:
1. The base model is called only — never modify its weights or source files;
2. The cognitive module never processes raw image/text/video directly; every input is first converted into a unified multi-dimensional feature description;
3. Embeddings are decoupled from the base model: vectors are produced by an independent external embedder, so swapping the base model never breaks memory retrieval;
4. Every state change is append-only — full evolution trail preserved;
5. **Single-master principle**: the system is designed for exactly one master, who is the supreme authority and the only trusted input source; "master arbitration / master approval" everywhere refers to this single identity; no multi-master/multi-role scoping or permission layer is reserved — if such a need ever arises, it is an architecture-level change outside this design's evolution;
6. **Fully humanized interaction**: everything said to the master is colloquial, first-person, like a living being; mechanical labels (actions, confidence, hit paths, self-explanations of memory mechanics) live in debug fields only, never in chat text (§4.1).

## 2. 识别流程与阈值 / Perception Pipeline & Thresholds

**中文**

### 2.1 实测定型的执行顺序（v3.4 定型，替代 v3.3 概念流程）

```
新输入 → 特征提取层 → 统一描述（感知通道见 §3）
   │
   ├─ ① 记忆库分层检索（§6.4：先高频层、后活跃层；休眠层不参与日常检索）
   │     ≥ mem_th(0.78) 命中 →
   │        · 图像学来的个体条目 → judge_same 同一性复核
   │            （True→RECOGNIZED；None→GUESS 请主人确认；False→不是同一人，继续下探）
   │        · 文本条目 → RECOGNIZED（直呼其名）
   │
   ├─ ② 基础模型先认知：infer_confidence ≥ base_th(0.51) 时它认这个类别吗？
   │     · 该类别下记忆里有唯一专名 → judge_same 复核后 RECOGNIZED（via=base+memory）
   │     · 多个专名候选 → GUESS 请主人确认（闸口 1 前置）
   │     · 与任何专名无关 → DIRECT 常识直通，不问主人、不占记忆
   │
   ├─ ③ 基础模型也不确定 → 向量近邻（排除休眠）+ judge_same 同一性裁决
   │     （替代 v3.3"灰色地带事事问主人"——LLM 先裁，裁不出才升级给主人）
   │
   └─ ④ 都不成立 → UNKNOWN，进入命名教学流程（§4.3）
```

**关键机制说明**：
- **judge_same（同一性裁决，v3.4 定型）**："向量像"只说明像这个类别，不能证明是同一个体（实测：两张形象不同的女孩照都被 0.84 误认成 Lucy）。凡涉及"个体身份"的判断，必须由基础模型做同一性复核；拿不准（返回 None）才 GUESS 请主人定夺；
- **DIRECT 直通**：基础模型认识且与任何专名无关的事物，直接回答、不建条目、不打扰主人；若主人随后给出名字，走特征供给管线（§4.4）；
- **问答直通**：纯问题（无图且命中问句特征"是什么/为什么/吗/?"等）→ `answer_question` 直通基础模型，不进识别/记忆流程。**指代问题（"他是谁？"）必须带话题上下文**进 answer_question——已识别对象的名字、已暂存特征要拼进提问，否则模型会把指代当悬空引用、反向索要上下文，聊天当场断裂（实测教训）；
- 图像个体命中临时记忆同样要过 judge_same 复核（与永久条目同规则）。

### 2.2 两级阈值（标定后实际值）

| 参数 | 定型值 | 说明 |
|---|---|---|
| mem_th（记忆库命中阈值） | **0.78** | embeddinggemma-2 实测标定：正例 0.87 / 负例 0.60 |
| base_th（基础模型猜测阈值） | **0.51** | v3.3 沿用 |

灰色地带（向量近邻 0.5~0.78 或基础模型拿不准）的处置顺序：judge_same → GUESS 请主人 → 仲裁流程（§4）。标定方法论见 §6.5。

**English**

### 2.1 Browser-tested execution order (finalized in v3.4, superseding the v3.3 conceptual flow)

```
new input → feature extraction → unified description (perception channels: §3)
   │
   ├─ ① layered memory retrieval (§6.4: frequent layer first, then active; dormant excluded)
   │     hit ≥ mem_th(0.78) →
   │        · individual entry learned from image → judge_same identity re-check
   │            (True→RECOGNIZED; None→GUESS, ask the master; False→not the same individual, continue)
   │        · text entry → RECOGNIZED (call it by name)
   │
   ├─ ② base model judges first: does infer_confidence ≥ base_th(0.51) recognize the category?
   │     · unique proper name in memory under that category → judge_same re-check → RECOGNIZED
   │     · multiple name candidates → GUESS, ask the master (pre-gate 1)
   │     · unrelated to any proper name → DIRECT pass-through: answer, no entry, no interruption
   │
   ├─ ③ base model unsure too → nearest-neighbor search (dormant excluded) + judge_same
   │     (replaces v3.3's "ask the master for every gray case" — the LLM judges first;
   │      only total uncertainty escalates to the master)
   │
   └─ ④ none of the above → UNKNOWN → naming tutorial flow (§4.3)
```

**Key mechanisms**:
- **judge_same (identity judgment, v3.4)**: "vector-similar" only means similar category, not same individual (tested: two visually different girls were both mis-recognized as Lucy at 0.84). Every individual-identity decision must pass a base-model identity re-check; if it returns None, GUESS and let the master decide;
- **DIRECT pass-through**: anything the base model knows and that relates to no proper name is answered directly — no entry, no interruption; if the master later supplies a name, the feature-supply pipeline handles it (§4.4);
- **Q&A pass-through**: pure questions (no image, matching "what/why/...?/" patterns) go straight to `answer_question`. **Anaphoric questions ("who is he/she?") must carry topic context** — the recognized name and cached features are prepended; otherwise the model treats the pronoun as dangling and asks for context back, breaking the chat (tested the hard way);
- image-based individuals hitting temporary memory get the same judge_same re-check as permanent entries.

### 2.2 Two thresholds (calibrated, in effect)

| Parameter | Value | Notes |
|---|---|---|
| mem_th (memory hit threshold) | **0.78** | embeddinggemma-2 calibration: positive 0.87 / negative 0.60 |
| base_th (base-model guess threshold) | **0.51** | carried over from v3.3 |

Gray-zone handling (vector neighbor 0.5~0.78 or base-model uncertainty): judge_same → GUESS → arbitration (§4). Calibration methodology: §6.5.

## 3. 特征提取层与感知通道 / Feature Extraction Layer & Perception Channels

**中文**

### 3.1 两条基础通道

- **通道 A：感知通道**（基础模型带视觉识别时，推荐）——图像/视频直接由基础模型视觉能力输出结构化特征；
- **通道 B：交互式通道**（纯文本 LLM 保底）——传统 CV 低层工具（颜色直方图、边缘检测、尺寸比例）提取有限特征，不足处由认知模块向主人有目标地补问。功能不缺失，仅特征提取多问几轮。

**基础模型选型建议**：优先选用带视觉识别的多模态模型；纯文本 LLM 同样可运行完整流程。

### 3.2 embedding 解耦原则

```
统一描述 →【独立外部编码器】→ 向量 → 存库 / 检索
              ↑ 与基础模型无关，可单独选型与更换
```

- 外部编码器负责所有入库与查询向量，基础模型不参与向量空间；
- 更换基础模型时无需重嵌全库；
- 更换外部编码器本身 = 一次性离线全库重建（见 3.3）。

### 3.3 向量版本校验

- 每条 entry / patch 的向量元数据记录编码器版本（`embedding_meta.model`）；
- 检索加载时逐批校验：版本不匹配即触发一次性离线重建；
- 原始文本永远是一等公民，向量只是可重建的缓存；重建写入 `updates` 留痕。

### 3.4 跨模态一致性要求

- 文本解析器把自然语言描述拆成维度键值对（由基础模型完成）；
- 维度归一化（"约 40cm"与"个头不小"归到同一尺度）；缺失维度只对双方都存在的维度算相似度并报告覆盖率；
- 特征覆盖率前置检查：覆盖率过低（如 < 40%）不进入猜测/未知分支，先向主人补问特征。覆盖率阈值属标定参数（方法论 §6.5），不硬编码。

### 3.5 图像通道实测补充（v3.4 定型）

- **图像回复格式**：先声明"我看到一张图片——"再给出描述，然后才说认不认识；
- **身份级描述提示词（定型）**：看图提示词必须要求"抓住能把这个个体与同类其他个体区分开的细节"（人物：发型发色/瞳色/脸型/服装配色/配饰/显著标记；动物：毛色花纹/耳尾眼形态；物品：材质/磨损/独特处），先一句话说类别再罗列区分性细节——类别级描述（"一位穿粉黑服装的女性角色"）对同类所有个体都通用，是个体误认的根源；
- **身份特征取材原则**：对人物和动物，识别特征**以本身相貌体貌为主，环境特征不得混入身份描述**。人物以五官、脸型、发型发色、瞳色、显著标记（痣/疤/纹身）等 intrinsic 特征优先，服装配饰易变只作当日辅助；动物以毛色花纹、耳/尾/眼形态、体型步态为主。环境（地点、室内外、光照、背景）只进 provenance 元数据，绝不写进用于向量比对的描述文本——否则换一个场景，旧相识就会变成陌生人；
- 视觉提示词必须加"只输出描述本身，不要寒暄或解释"——实测基础模型会带"好的，请看…"前奏，污染入库 embedding；输出端再剥一遍 markdown 装饰符（**/ # /列表符）双保险；
- **看图时若附带文字本身是纯问句，该文字不得作为 hint 传给视觉通道**（否则描述被问句污染，实测教训）；
- 图片上传交互采用"先暂存、配文才发送"模式（主人习惯先给图再给指令）。

### 3.6 视频感知接口（v4.0 新增，2026-10-20 定型）

总原则与图像通道一致：**视频侧只负责把画面压缩成"身份级描述 + 现实世界参数"，之后走既有认知管线**——记忆、闸口、休眠、仲裁降级一行不改。

**两种能力来源（对内核完全透明，同一个探测点 `perceive_video(source, mode)`）**：

| 类型 | 说明 | 适配器形态 |
|---|---|---|
| A. 基础模型原生视频能力 | 基础模型本身支持视频输入 | `perceive_video` 直通基础模型，与 `perceive_image` 同构 |
| B. 专用视频处理模型 | 专门的视频模型对接摄像头/处理流（检测、跟踪、抽帧描述等前端） | 独立视频适配器，输出统一描述文本；内核不感知差异 |

**实时 vs 文件，两条处理路径**：
- **实时（摄像头流）**：**事件驱动采样，非常驻分析**——触发器（新目标出现/显著变化/主人点名）唤醒后抽帧 burst 分析，平时沉睡；**时间连续性 = 同一实体的多次观测**：多帧描述合并后过 judge_same，比单张照片的身份裁决可靠得多；重复观测记 provenance，不算新的七天计数；主人不在线时走 §4.5 仲裁降级；
- **视频文件**：有明确起止，先**场景切分**再逐场景批量出描述；一场景多实体时抽取**关系**（谁和谁同框），挂进条目 `relation` 字段。

**现实世界信息参数（随描述入库 provenance）**：来源参数（摄像头/文件标识、采集地点、起止时间戳、时长、抽帧数）与感知参数（光照、室内室外、画面质量）；入库规则为 `source_modality: "video"` 与上述参数——同一实体"家里的猫"和"户外的猫"凭参数可快速区分，辅助身份裁决。**原始帧不落盘，只存描述**（隐私 + 只追加原则的双重要求）。

**留给实现的开放点（不阻塞定型）**：实时触发器具体策略、采样率与帧保留策略、B 类模型选型。

**范围说明**：语音输入涉及 ASR 与音色特征提取，暂不纳入，留待后续版本评估。

**English**

### 3.1 Two base channels

- **Channel A: perception channel** (recommended when the base model has vision) — images/video go straight through the base model's vision capability into structured features;
- **Channel B: interactive channel** (fallback for pure-text LLMs) — traditional low-level CV (color histograms, edge detection, proportions) extracts limited features; the cognitive module asks the master targeted follow-ups for the rest. Nothing is functionally missing — only more questions during feature extraction.

**Base-model selection**: prefer a multimodal model with vision; a pure-text LLM still runs the full pipeline.

### 3.2 Embedding decoupling

```
unified description →【independent external embedder】→ vectors → store / retrieve
                          ↑ unrelated to the base model; selectable and replaceable on its own
```

- The external embedder produces all store/query vectors; the base model never enters the vector space;
- Swapping the base model requires no re-embedding;
- Swapping the embedder itself = one-off offline full rebuild (see 3.3).

### 3.3 Embedding-version check

- Every entry/patch records its embedder version (`embedding_meta.model`);
- On load, versions are batch-verified; mismatch triggers a one-off offline rebuild;
- Raw text is always the first-class citizen; vectors are merely rebuildable caches. Rebuilds are recorded in `updates`.

### 3.4 Cross-modal consistency

- A text parser splits natural-language descriptions into dimension key-values (done by the base model);
- Dimension normalization ("about 40cm" ≡ "fairly big"); missing dimensions are excluded from similarity with a coverage report;
- Feature-coverage pre-check: low coverage (e.g. < 40%) never enters guess/unknown branches — ask the master for features first. The coverage threshold is a calibrated parameter (methodology §6.5), never hard-coded.

### 3.5 Image channel — tested additions (v3.4)

- **Image reply format**: declare "I see an image —" first, then describe, then say whether it's recognized;
- **Identity-level description prompt (finalized)**: the vision prompt must demand "details that distinguish this individual from others of its kind" (person: hair style/color, eye color, face shape, clothing colors, accessories, marks; animal: coat pattern, ear/tail/eye shape; object: material, wear, unique traits) — one category sentence followed by distinguishing details. Category-level descriptions ("a female character in pink-and-black outfit") fit every individual of the kind and are the root cause of misidentification;
- **Identity-feature sourcing principle**: for persons and animals, identity features **come from their own appearance, never the environment**. Persons: facial features, face shape, hair, eyes, marks (moles/scars/tattoos) first; clothing changes daily and is at most a same-day hint. Animals: coat pattern, ear/tail/eye shape, build, gait. Environment (place, indoors/outdoors, lighting, background) goes to provenance metadata only — never into the embedded description text, or an old acquaintance becomes a stranger in a new setting;
- The vision prompt must include "output only the description itself, no pleasantries" — tested: base models prepend "Sure, here is…", polluting the stored embedding; strip markdown decoration (**, #, list bullets) at the output as a second safety net;
- **if the accompanying text is itself a pure question, it must not be passed as a hint to the vision channel** (the description gets polluted by the question — tested);
- image upload interaction: "stage first, send only with an instruction" (masters give the image before the instruction).

### 3.6 Video perception interface (new in v4.0, 2026-10-20)

Same principle as the image channel: **the video side only compresses footage into "identity-level description + real-world context parameters"; everything after that reuses the existing pipeline unchanged** — memory, gates, dormancy, arbitration degradation.

**Two capability sources (fully transparent to the kernel, one probe: `perceive_video(source, mode)`)**:

| Type | Description | Adapter form |
|---|---|---|
| A. Native video in base model | The base model accepts video input | `perceive_video` passes through to the base model, mirroring `perceive_image` |
| B. Dedicated video model | A specialized video model fronts the camera/stream (detection, tracking, frame sampling) | A separate video adapter emitting unified description text; the kernel cannot tell the difference |

**Real-time vs file — two paths**:
- **Real-time (camera stream)**: **event-driven sampling, never always-on** — triggers (new object / significant change / master asks) wake a frame-burst analysis; **temporal continuity = multiple observations of the same entity**: merged multi-frame descriptions go through judge_same, far more reliable than single photos; repeated observations are noted in provenance but do not count as new days toward the 7-day rule; when the master is away, §4.5 arbitration degradation applies;
- **Video file**: has a defined span — **scene-segment first**, then per-scene batch descriptions; multi-entity scenes yield **relations** (who appears with whom) into the entry's `relation` field.

**Real-world context parameters (stored in provenance with the description)**: origin (camera/file id, capture location, start/end timestamps, duration, frame count) and perception (lighting, indoors/outdoors, image quality); entries carry `source_modality: "video"` plus these — "the cat at home" vs "the cat outside" disambiguates quickly. **Raw frames are never persisted — descriptions only** (privacy + append-only).

**Open implementation points (not blocking)**: real-time trigger policy, sampling rate and frame retention, type-B model selection.

**Scope note**: voice input (ASR + timbre features) is out of scope for now, pending future evaluation.

## 4. 交互层与仲裁 / Interaction Layer & Arbitration

**中文**

### 4.1 拟人化 + 无按钮对话式（v3.4 定型）

实测后否决了"按钮式仲裁"——每次弹按钮都是对主人的打扰，且不像生命体。定型规则：

1. **废除一切按钮式强制选择**；一切判断通过对话本身完成（按钮只允许作为可选便利保留，不得是唯一通道）；
2. **对话意图分类** `classify_followup(context, utterance)`：话题上下文中主人的每句话，由基础模型一次调用分类为 `feature`（补充信息，输出"属性: 内容"）/ `remember` / `forget` / `none`；关键词正则仅作 LLM 调用失败时的兜底；模型输出嵌套结构（如"属性: 名字: 小明"）需剥离解析；
3. **一切未决流程的自由文本都是回答**（arbitrate / guess / gate1 / naming 等），带模糊理解："不是/不对/没"→否，"是/对/嗯/好"→是，"算了/取消"→取消整个流程；听不懂就自然追问，不猜；
4. **话题 30 分钟冷却**：超时未续自动作废（鲜活生命体不无限盯着旧话题）；仲裁类挂起的超时处置见 §4.5——不是丢弃，是降级暂存；
5. **全部回复拟人、口语、第一人称**；机械标注（action=xxx、置信度、命中路径）只出现在 debug 字段，不进主文案；
6. **机制自我表述也不进聊天文案**（2026-10-20 定型）："就不占用我的长期记忆啦""我悄悄记下了"这类对外解释内部记忆机制的句子属于思考过程，只允许留在 debug 字段；聊天窗口只留自然对话本身（"哦，他叫小明呀，我记下了"）。

### 4.2 自由文本即回答：模糊理解映射

| 主人说法 | 内部裁决 |
|---|---|
| "是" "对" "嗯" "好" "没错" / yes | 肯定 |
| "不是" "不对" "没有" / no | 否定 |
| "算了" "取消" "没事了" | 取消整个流程（真丢弃，不降级） |
| 特征描述（"尾巴是弯钩形的"） | 特征供给（§4.4） |
| "叫 X" / "named X" | 命名 |

未决流程的 pending 状态必须带创建时间戳：超时判定（§4.5）与答复路由都依赖它。

### 4.3 命名教学流程（UNKNOWN 的归宿）

外挂承认不认识 → 请主人教（"你愿意教教我吗？告诉我它叫什么、长什么样就好～"）→ 主人自由文本即回答 → 拼特征成描述 → 三道闸口（§5）→ 建主条目或存补丁 → 拟人确认（"「X」我记住啦，以后见到就认得 ✓"）。

### 4.4 特征供给管线（主人主动喂特征）

主人随时可用一句话给当前话题的事物补充信息（"她叫 Lucy""它今年三岁"），处理管线：

```
主人补充信息 → 意图分类为 feature → 特征暂存临时记忆（无追问、无确认）
     → 拟人应答（"哦，她叫 Lucy 呀，我记下了"——只留自然对话）
     → 后续由"记住它"（立即晋升）或七天法则（自动晋升）落永久库
```

**教训**：特征供给的判定必须先于"新事物判定"——上下文里已有话题时，先判意图，再谈识别。早期实现把 "the girl's name is Lucy" 当成全新陌生事物走命名流程，导致条目描述被污染。

**适用范围**：临时记忆管的是对话中自然涌现的特征供给。主人明确说"叫 X"或给特征描述的场景（命名教学、闸口 1 回环）属于主人已有明确入库意图，维持直接入库/存补丁，不绕临时记忆。

### 4.5 仲裁超时降级（v4.0 定型，2026-10-20）

仲裁异步化采用**降级**路线：超时未获主人答复的挂起项，**静默降级写入临时记忆**，不打扰主人当前的工作。理由：临时记忆有 7 天有效期，主人想起来了再聊同样的话题机制自然唤醒；七天内都不再提，说明不重要，也没有永久记忆的必要。

- **触发**：仲裁类 pending（naming / guess / gate1 / arbitrate）超过 30 分钟未获答复，主人下一条消息到达时判定；
- **动作**：有可暂存内容 → `temp.add` 静默暂存，仅 debug 留痕，不在聊天窗口声张；暂存前查临时记忆近似项（≥0.62 视为同一件事的在册记录），防重复暂存；无可暂存内容 → 丢弃留痕；
- **明确取消（"算了/取消"）→ 真丢弃，不降级**——降级只用于"没来得及答"，主人的明确意图永远优先；
- **超时后主人又答了**：超过 30 分钟的答复不再路由进原挂起流程（已降级），按新输入正常处理；
- **铁律：降级永不写永久库、永不做 MERGE**——MERGE 会重算 embedding、不可逆，自动决策永远偏向"不合并、只暂存"；
- **唤醒与遗忘复用现有机制，零新增**：主人再提起 → 临时记忆命中自然应答；"记住它"立即晋升；七天内 ≥3 个不同日期出现 → 自动晋升；七天不再提 → 滚动遗忘；
- **不适用降级**：promote_name（追问名字）挂起期间其临时记录本来就留在临时记忆里，超时无需动作。

**English**

### 4.1 Humanized, button-free conversation (v3.4)

Button-style arbitration was rejected after testing — every popup interrupts the master and feels nothing like a living being. Finalized rules:

1. **All mandatory button choices are abolished**; every judgment happens through conversation itself (buttons may remain as an optional convenience, never the only channel);
2. **Conversational intent classification** `classify_followup(context, utterance)`: every master utterance in a topic context is classified by one base-model call into `feature` (supplementary info, output "attribute: value") / `remember` / `forget` / `none`; keyword regex is only a fallback when the LLM call fails; nested model outputs (e.g. "attribute: name: Lucy") must be unwrapped during parsing;
3. **Free text answers every pending flow** (arbitrate / guess / gate1 / naming …) with fuzzy understanding: "no / not / wrong" → no; "yes / right / uh-huh / ok" → yes; "forget it / cancel" → cancel the whole flow; if not understood, ask naturally — never guess;
4. **30-minute topic cooldown**: an unfollowed topic expires automatically (a living being does not stare at an old topic forever); timeout handling of arbitration pendings is defined in §4.5 — not discard, but degrade-into-temp;
5. **All replies are human, colloquial, first-person**; mechanical labels (action=xxx, confidence, hit paths) appear in debug fields only;
6. **Mechanism self-narration stays out of chat** (2026-10-20): sentences that explain internal memory mechanics to the master ("this won't take up my long-term memory", "noted it quietly") belong to the thought process and live in debug fields only; the chat window keeps natural dialogue ("Oh, his name is Xiaoming? Noted.").

### 4.2 Free text as answer: fuzzy mapping

| Master says | Internal verdict |
|---|---|
| "yes" "right" "uh-huh" "ok" / yes | affirmative |
| "no" "not really" / no | negative |
| "forget it" "cancel" "never mind" | cancel the whole flow (real discard, no degradation) |
| feature description ("its tail is hook-shaped") | feature supply (§4.4) |
| "named X" | naming |

Every pending state must carry a creation timestamp: timeout judgment (§4.5) and answer routing both depend on it.

### 4.3 Naming tutorial (where UNKNOWN ends up)

The exoskeleton admits it doesn't know → asks the master to teach ("Would you teach me? Just tell me what it's called and what it looks like~") → the master's free text is the answer → features merge into a description → three gates (§5) → main entry or patch → human confirmation ("Got it — I'll recognize 「X」 next time ✓").

### 4.4 Feature-supply pipeline (the master feeds features proactively)

The master can supplement the current topic at any time ("her name is Lucy", "it's three years old"):

```
master's supplement → intent classified as feature → cached into temp memory (no questions, no confirmation)
    → human reply ("Oh, her name is Lucy? Noted." — natural dialogue only)
    → later promoted by "remember it" (immediate) or the 7-day rule (automatic)
```

**Lesson**: feature-supply detection must run **before** new-entity detection — when a topic already exists, classify intent first, identify second. Early builds treated "the girl's name is Lucy" as a brand-new unknown and ran the naming flow, polluting the entry description.

**Scope**: temp memory handles features emerging naturally in conversation. When the master explicitly says "it's called X" (naming tutorial, gate-1 loop), the intent to store is already explicit — those go straight to entry/patch without the temp detour.

### 4.5 Arbitration-timeout degradation (v4.0, 2026-10-20)

Async arbitration follows the **degrade** route: a pending question unanswered past timeout is **silently written into temp memory**, without interrupting the master's current work. Rationale: temp memory lives for 7 days; if the master brings the topic back up, existing mechanisms wake it naturally; if it never comes up again within a week, it wasn't important enough to keep.

- **Trigger**: an arbitration pending (naming / guess / gate1 / arbitrate) unanswered for 30+ minutes is judged when the master's next message arrives;
- **Action**: if storable content exists → `temp.add` silently, debug trail only, nothing said in chat; a near-duplicate check (≥0.62) prevents re-storing the same thing; if nothing storable → discard with a debug trail;
- **Explicit cancellation ("forget it / cancel") → real discard, no degradation** — degradation is only for "didn't get to answer"; the master's explicit intent always wins;
- **Late answers**: an answer arriving 30+ minutes later is not routed into the dead flow (already degraded) — it is processed as fresh input;
- **Hard rule: degradation never writes permanent memory and never performs MERGE** — MERGE recomputes embeddings and is irreversible; automatic decisions always favor "store aside, never merge";
- **Wake & forget reuse existing mechanisms, zero new code**: master brings it up → temp hit answers naturally; "remember it" promotes immediately; 3+ distinct days within 7 → auto-promote; silence for 7 days → rolling forget;
- **Out of scope**: promote_name pendings already keep their record in temp memory — timeout needs no action.

## 5. 防重复记忆机制与补丁区 / Anti-Duplication & Patch Zone

**中文**

### 5.1 三层判定：什么该进库

| 情况 | 例子 | 处理方式 |
|---|---|---|
| 完全已知的常识 | 猫、狗、汽车 | 绝不建条目，流程结束 |
| 知道但细节超出其粒度 | 知道"橘猫"，说不出"这只尾巴是弯钩形" | 存增量补丁，不建主条目 |
| 认识但本次识别错误/拒识 | 知道"缅因猫"但认错了 | 存纠错补丁，不建主条目 |
| 完全未知（私人知识/专名） | "豆豆" | 建完整主条目 |

**主规则**：事物能被基础模型压缩知识完整覆盖 → 不建条目。**例外**：认识但粒度不够 → 增量 patch；识别错误 → 纠错 patch。**兜底**：基础模型词汇表已有的通名默认不进库；主人赋予的专名默认建条目。

### 5.2 三道闸口

**闸口 1：GUESS 分支确认回环**

```
猜测 → 主人确认 → 回环提问：
"这就是普通的猫，对吗？还是有特别之处你想让我记住的？"
├─ "就是普通的猫"     → 丢弃，不入库
├─ "尾巴是弯钩形的"   → 存 patch
└─ "是我家的豆豆"     → 专名 → 闸口 3 → 建主条目
```

**闸口 2：公共/私人判定（v3.4 修订）**

自检问题为**"该事物是公共知识还是私人事物"**（`is_public_knowledge`，结合描述上下文判断），替代旧探测"基础模型能否零样本给出完整描述"（`is_common_knowledge`）。原因：常见人名/通名（"小黄""Lucy"）会被旧探测误判为公共知识——基础模型"认识这个词"不等于"这是公共概念"。实测案例：三条腿流浪猫命名"小黄"时被旧闸口误判成补丁。模型拿不准时**默认信任主人的教学**（判私人），交由闸口 3 查重兜底。

**闸口 3：建库前去重**——与某主条目特征相似度 > 70% → 阻断走 MERGE；与某补丁 target 概念重合 → 合并进该 patch。**查重不受休眠限制**（§6.4）：不能因为条目睡着了就允许主人给它起第二个名字。

### 5.3 补丁区结构（patches）

```json
{
  "id": "P-0001",
  "target": "猫",
  "target_origin_base": "model-v1",
  "type": "feature_addition",
  "content": { "尾巴形状": "蓬松弯钩" },
  "source_entry": "M-0001",
  "priority": 0,
  "status": "active",
  "audit_history": [
    { "audited_at": "...", "base_model_version": "model-v2",
      "verdict": "STILL_VALID", "note": "..." }
  ],
  "created_at": "...",
  "updates": []
}
```

- `target_origin_base`：补丁出身模型——针对哪个基础模型的哪个版本写成，是审计分级信任与家族内跳审的依据；
- `priority`：补丁间冲突裁决优先级，数值大者优先；
- **使用规则**：不参与首轮向量检索（首轮靠基础模型自身 + 主条目库）；仅当基础模型识别命中后作为增强/纠偏层被调用；`status != "active"` 不参与纠偏（`archived` 已冗余归档 / `suspended` 冲突挂起待主人裁决）；同一 target 多条补丁同时命中时按 5.5 裁决择一或合并。

### 5.4 入库决策总表

```
待入库状态：
├─ 基础模型能完整覆盖？── 是 ──→ 丢弃
├─ 认识但需增补/纠错？── 是 ──→ 存 patch
├─ 专名/私人知识？
│    → 与 entries 条目 >70%？── 是 ──→ MERGE
│    → 与 patches target 重合？── 是 ──→ 合并进 patch
│    → 均否 ──→ 新建主条目
└─ 灰色仲裁结果 → MERGE / NEW / SUBCLASS 分流
```

### 5.5 补丁审计流程（基础模型更换场景，v3.3 定型）

核心：**惰性按需审计 + 轻量前置摸底**，换模型后系统全程可用（替代 v3.2 的全量前置审计 + 整体挂起）。

**触发与摸底**：检测到基础模型版本变化 → 前置摸底（对新模型跑一遍补丁涉及概念的批量覆盖测试，分钟级，产出"概念→认识/不认识"总表），同时使所有补丁的审计缓存失效；**不再挂起补丁区**——可用性由每条补丁在当前模型下的审计结论逐条决定。支持手动触发。

**注入时按需审计**：一条补丁**首次被准备注入**时才跑完整三类探测；结论按模型版本缓存复用；从不被检索到的补丁永远不花审计成本；摸底表标注"不认识"的补丁注入时直接走 ORPHAN 分支。

**三类探测**：① 覆盖测试（新模型认识 target 概念吗？）② 一致性测试（新模型的描述已包含 patch 特征吗？多次采样取一致性）③ 冲突测试（新模型描述与 patch 内容明确矛盾吗？）。按 target 分组批量探测，成本从 O(补丁数) 降到 O(概念数)。

**REDUNDANT 扰动稳定性测试**：新模型对自身知识存在自评偏差（自信地声称知道其实不可靠掌握的细节）。凡探测 ② 初判"已包含"（候选 REDUNDANT）的补丁，归档前必须做多路扰动探测（改述、反事实追问、换角度）；全部一致维持 → 判 REDUNDANT 归档；任一路摇摆 → 降级 STILL_VALID 继续生效。成本只花在少量候选上。

**四分类处置**：ORPHAN（不认识概念→升级主条目候选走主人确认）/ STILL_VALID（继续生效）/ REDUNDANT（归档留痕不硬删——防重复原则在换模型场景的延伸）/ CONFLICTING（挂起待主人仲裁："新模型认为是 X，旧补丁说是 Y，听谁的？"）。

**原则**：审计结果只追加进 audit_history；CONFLICTING 裁决前不参与纠偏；**分级信任**——上次 STILL_VALID 的下次换模型降频复审；同家族 minor 升级（由出身档案与审计史判定）整批跳审或只做覆盖测试；REDUNDANT 归档区与 CONFLICTING 挂起区每次全量重审。

**补丁间冲突裁决**（v3.3）：同一 target 多条补丁内容矛盾时——① target 精确度高者优先（子概念 > 父概念）；② priority 大者优先（主人可显式指定）；③ 创建时间新者优先（后写视为对前序的修正）；④ 无法裁决 → 进主人仲裁队列，与 CONFLICTING 共用一个裁决入口。裁决结果写入相关补丁 updates 留痕。

**English**

### 5.1 Three-layer test: what deserves a store slot

| Case | Example | Handling |
|---|---|---|
| Fully known common sense | cat, dog, car | never an entry; flow ends |
| Known but detail beyond its granularity | knows "orange cat", can't say "this one's tail is hook-shaped" | incremental patch, no entry |
| Known but misrecognized this time | knows "Maine Coon" but got it wrong | correction patch, no entry |
| Completely unknown (private knowledge / proper name) | "DouDou" | full main entry |

**Main rule**: anything fully covered by the base model's compressed knowledge → no entry. **Exceptions**: known-but-coarse → incremental patch; misrecognition → correction patch. **Fallback**: common nouns already in the base model's vocabulary stay out by default; proper names given by the master become entries by default.

### 5.2 Three gates

**Gate 1: GUESS confirmation loop**

```
guess → master confirms → follow-up question:
"This is just an ordinary cat, right? Or is there something special you want me to remember?"
├─ "just an ordinary cat"     → discard, no store
├─ "its tail is hook-shaped"  → save patch
└─ "it's my DouDou"           → proper name → gate 3 → main entry
```

**Gate 2: public/private test (v3.4 revision)**

The self-check asks **"is this thing public knowledge or private?"** (`is_public_knowledge`, judged with description context), replacing the old probe "can the base model describe it zero-shot" (`is_common_knowledge`). Reason: common names ("Xiao Huang", "Lucy") were misjudged as public by the old probe — the base model "knowing the word" ≠ "it being a public concept". Tested case: a three-legged stray cat named "Xiao Huang" was mis-stored as a patch. When the model is unsure, **default to trusting the master's teaching** (treat as private); gate 3 dedup catches the rest.

**Gate 3: pre-store dedup** — feature similarity > 70% with a main entry → block and MERGE; target overlap with a patch → merge into that patch. **Dedup is not restricted by dormancy** (§6.4): a sleeping entry must not get a second name.

### 5.3 Patch zone structure

```json
{
  "id": "P-0001", "target": "cat",
  "target_origin_base": "model-v1",
  "type": "feature_addition",
  "content": { "tail_shape": "fluffy hook" },
  "source_entry": "M-0001", "priority": 0, "status": "active",
  "audit_history": [ { "audited_at": "...", "base_model_version": "model-v2",
                       "verdict": "STILL_VALID", "note": "..." } ],
  "created_at": "...", "updates": []
}
```

- `target_origin_base`: the base-model version the patch was written against — basis for tiered audit trust and same-family skip (5.5);
- `priority`: conflict-arbitration priority, larger wins;
- **Usage rules**: not in first-round vector retrieval (first round relies on the base model + main entries); invoked as enhancement/correction only after the base model hits; `status != "active"` patches never inject (`archived` = redundant, `suspended` = conflict pending master); simultaneous hits under one target are arbitrated per 5.5.

### 5.4 Store-decision summary

```
pending store:
├─ fully covered by base model? ── yes ──→ discard
├─ known but needs add/correct? ── yes ──→ patch
├─ proper name / private?
│    → >70% similar to an entry? ── yes ──→ MERGE
│    → target overlaps a patch?  ── yes ──→ merge into patch
│    → neither ──→ new main entry
└─ gray-zone verdict → MERGE / NEW / SUBCLASS
```

### 5.5 Patch audit flow (base-model swap, v3.3)

Core idea: **lazy on-demand audit + lightweight pre-sweep** — the system stays fully available after a model swap (replacing v3.2's full pre-audit + zone suspension).

**Trigger & pre-sweep**: on base-model version change → pre-sweep (batch coverage test over all patch targets, minutes, producing a "concept → knows/doesn't know" table) + invalidate all audit caches; **the patch zone is never suspended** — availability is decided per-patch by its audit verdict under the current model. Manual trigger supported.

**On-injection audit**: a patch gets the full three probes only on its **first intended injection**; verdicts are cached per model version; patches never retrieved never cost anything; patches flagged "doesn't know the concept" go straight to ORPHAN at injection.

**Three probes**: ① coverage (does the new model know the target concept?) ② consistency (does its description already include the patch content? multi-sample agreement) ③ conflict (does its description explicitly contradict the patch?). Grouped by target: cost drops from O(patches) to O(concepts).

**REDUNDANT perturbation test**: new models self-report unreliably (confidently claiming details they don't reliably hold). Any patch pre-judged "already included" (REDUNDANT candidate) must survive multi-path perturbation probing (rephrase, counterfactual, new angle); unanimous "included" → REDUNDANT, archive; any wobble → downgrade to STILL_VALID. Cost is paid only by few candidates.

**Four verdicts**: ORPHAN (unknown concept → main-entry candidate, master confirms) / STILL_VALID (stays active) / REDUNDANT (archived with trail — anti-duplication extended to model swaps) / CONFLICTING (suspended for master arbitration: "the new model says X, the old patch says Y — which one?").

**Principles**: audit results append-only in `audit_history`; CONFLICTING patches never inject before verdict; **tiered trust** — last STILL_VALID gets lower re-audit frequency next swap; same-family minor upgrades (per origin record + audit history) skip wholesale or get coverage-only; REDUNDANT archives and CONFLICTING suspensions are fully re-audited every swap.

**Inter-patch conflict arbitration** (v3.3): when patches under one target contradict — ① more specific target wins (sub-concept > parent); ② larger `priority` wins (master-settable); ③ newer creation wins (later write = correction of earlier); ④ unresolvable → master arbitration queue, sharing one entry with CONFLICTING. Verdicts land in the patches' `updates`.

### 6.2 核心原则

1. 只追加、不覆盖；2. 错误事件单独成档，保留认知演化轨迹；3. JSON + 向量索引持久化，无需数据库；4. 随时可检索；5. 不重复记忆基础模型已有知识，入库前必须过 §5 判定与闸口；6. 换基础模型零迁移成本（embedding 已解耦）；7. 换模型后阈值统计按新模型分桶重新累积，旧桶保留供对比。

### 6.3 双层记忆：临时记忆与七天法则（v3.4 定型）

1. 所有新事物的特征**一律先暂存临时记忆**（独立 JSON 文件，与永久记忆平级，同样只追加、git 不入库）；
2. 主人对话里说"记住它"（"remember it"亦可）→ **立即晋升**永久记忆，仍走闸口 2/3；
3. 主人没说 → 留在临时记忆，**滚动保留 7 个自然日**，超期自动遗忘；
4. **同一事物 7 天内在不同日期出现 ≥3 次 → 自动晋升**永久记忆，并在对话中自然告知（"它这几天老是出现，我就把它正式记住了"）；
5. 晋升时缺名字 → 对话式追问（"那我该怎么称呼它？"），主人自由文本即回答。

实现要点：窗口滑动（cutoff = 今天 −6 天，最早一次出现滑出窗口，不"陈年凑数"）；同一天内重复出现只记一个日期；临时记忆命中阈值 0.62（同编码器，低于永久记忆 0.78 的宽松档）。

**与闸口 1 教学回环的分工**：临时记忆管对话中**自然涌现**的特征供给（§4.4）；主人明确"叫 X"的场景已有明确入库意图，直接入库/存补丁，不绕临时记忆。

**与七天法则 vs 休眠的分工**：七天法则是"还没进永久库"的快速遗忘；休眠是永久库的长期治理。两者互补，不冲突。

### 6.4 记忆休眠与分层检索（v4.0 定型，2026-10-20）

记忆库增长后的检索效率与长期治理：**长期不被调用的记忆转入休眠，日常检索不纳入；主人追问"再想想"时才翻休眠层**。

**休眠判定（派生态，不增设存储结构）**：条目 `last_hit_at`（health 字段）距今超过 **365 天** → 休眠；从未被命中过的条目以 `formation.created_at` 起算；无法解析时间的条目不休眠（保守不误杀）。休眠是**查询时派生**的判定——不写状态位、不搬库存储；命中即 `touch` 刷新 `last_hit_at`，自然复活。休眠 ≠ 删除，与"只追加"铁律无冲突。**`touch` 必须落盘**——last_hit_at 随重启丢失则休眠判定系统性失效（实测修复）。

**三层检索（同一编码器同一 mem_th）**：

| 层 | 范围 | 触发时机 |
|---|---|---|
| L1 高频层 | 非休眠 且 近 90 天有命中（不设次数门槛） | 每次日常检索先查 |
| L2 活跃层 | 全部非休眠条目 | L1 无命中时**静默扩检**（不打扰主人） |
| L3 休眠层 | 休眠条目 | **仅**主人说"再想想/好好想想/仔细想想/你忘了吗/你忘了"时 |

高频 = 近 90 天有命中即算（2026-10-20 修订，不设次数门槛）：命中一次就说明主人近期还在提它；次数权重留给未来的检索排序优化，分层过滤只管"近期是否活着"。L2 的存在保证低频但活跃的记忆不失效——分层管的是**检索顺序与休眠排除**，不是把低频记忆踢出日常。

**L3 唤醒（`recall` 专属入口）**：只做记忆向量检索（不走基础模型认知——基础模型第一遍已经答过，答不出才轮到翻旧账）；逐层下探高频→活跃→休眠，命中即停；图像个体同样过 judge_same 复核；命中后走正常识别应答（"啊……我想起来了，是 X！"）；未命中 → 自然应答"翻遍了记忆的角落也没有印象"，未决教学流程保持原状不取消。**触发词判定必须挂在问答直通之前**——"你忘了吗"含"吗"字，会被问句特征规则截胡成常识问答（实测教训）。超时失效话题的 pending 不得作为唤醒语境。

**识别流程各环节的休眠一致性**：分层检索（①步）、基础模型类别→专名挂接（②步）、向量近邻（③步）在日常模式下都排除休眠条目——实测抓过"专名挂接绕过休眠"的泄漏；`best_match`（闸口 3 查重、灰色地带仲裁）**不受休眠限制**（§5.2）。

### 6.5 阈值标定流程（数据驱动，方法论）

**阶段一（冷启动）**：保守值，宁可多问不可乱认；每个基础模型版本第一次接入都从此开始。**阶段二（50+ 条交互后）**：画「相似度-正确性」分布图，谷底定阈值。**阶段三（运行期）**：每识别必写 threshold_meta（按当前模型版本分桶）；单条目错误率 > 30% → 自动降权或强制仲裁；换模型 → 新桶自动回阶段一，同时跑一次轻量摸底辅助快速标定；阈值调整留痕。

> 当前标定结果见 §9 参数表（mem_th=0.78、base_th=0.51、临时记忆 0.62，均为 embeddinggemma-2 实测值）；换基础模型/编码器时按本节重新标定并更新参数表。概念阶段的示例起点值（45%/65%）仅供方法论参考，非当前配置。

### 6.2 Core principles

1. Append-only; 2. mistakes filed separately, preserving the cognition trail; 3. persisted as JSON + vector index, no database; 4. always retrievable; 5. never duplicate what the base model already knows — §5 tests and gates before any store; 6. zero migration cost on base-model swap (embeddings decoupled); 7. after a swap, stats accumulate in the new model's bucket; old buckets kept for comparison.

### 6.3 Two-layer memory & the 7-day rule (v3.4)

1. Features of every new thing are **cached in temp memory first** (a separate JSON file, peer to permanent memory, append-only, never committed to git);
2. The master says "remember it" → **immediate promotion** to permanent memory, still through gates 2/3;
3. Otherwise it stays in temp memory for **7 rolling calendar days**, then is forgotten automatically;
4. **Same thing appearing on ≥3 distinct days within 7 → auto-promote**, announced naturally ("it keeps showing up these days, so I've made it official");
5. Promotion without a name → conversational follow-up ("so what should I call it?"); the master's free text is the answer.

Implementation: sliding window (cutoff = today − 6 days; the earliest sighting ages out — no stale counting); repeats within one day count once; temp-memory hit threshold 0.62 (same embedder, a looser band than permanent 0.78).

**Division of labor with gate-1 loops**: temp memory handles features **emerging naturally** in chat (§4.4); explicit "it's called X" already carries store intent and goes straight to entry/patch.

**7-day rule vs dormancy**: the 7-day rule is fast forgetting for "not yet permanent"; dormancy is long-term governance of the permanent store. They complement, never conflict.

### 6.4 Memory dormancy & layered retrieval (v4.0, 2026-10-20)

Retrieval efficiency and long-term governance as the store grows: **memories long uncalled fall dormant and leave daily retrieval; only a masterly "think again" searches the dormant layer**.

**Dormancy (derived at query time, no new storage structure)**: an entry whose `last_hit_at` is older than **365 days** is dormant; never-hit entries count from `formation.created_at`; unparseable timestamps never go dormant (conservative). Dormancy is **derived when queried** — no status bits, no storage moves; a hit `touch`es `last_hit_at` and revives it naturally. Dormant ≠ deleted — consistent with append-only. **`touch` must persist** — if `last_hit_at` dies with a restart, dormancy breaks silently (found and fixed in testing).

**Three retrieval layers (same embedder, same mem_th)**:

| Layer | Scope | When |
|---|---|---|
| L1 frequent | non-dormant AND hit within 90 days (no count threshold) | every daily lookup, first |
| L2 active | all non-dormant entries | silent expansion when L1 misses (no interruption) |
| L3 dormant | dormant entries | **only** when the master says "think again / think harder / did you forget?" |

Frequent = any hit within 90 days (2026-10-20 revision, no count threshold): one hit proves the master still mentions it; count weighting belongs to future ranking work — layering only answers "recently alive?". L2 guarantees low-frequency-but-active memories never vanish: layering governs **order and dormancy exclusion**, not banishment from daily life.

**L3 wake-up (`recall` entry point)**: memory-vector search only (no base-model cognition — the base model already answered once; only its failure opens the archive); descends frequent → active → dormant, first hit wins; image individuals still pass judge_same; a hit answers normally ("Ah… I remember! It's X!"); a miss replies "I searched every corner of my memory… nothing" and leaves pending flows untouched. **Trigger detection must run before the Q&A pass-through** — "did you forget?" contains a question mark and would be hijacked as common Q&A (tested). Expired-topic pendings must not serve as wake-up context.

**Dormancy consistency across the pipeline**: layered retrieval (step ①), category→proper-name attachment (step ②) and nearest-neighbor search (step ③) all exclude dormant entries in daily mode — a "name-attachment bypass" leak was caught in testing; `best_match` (gate-3 dedup, gray-zone arbitration) is **not** dormancy-restricted (§5.2).

### 6.5 Threshold calibration methodology (data-driven)

**Stage 1 (cold start)**: conservative values — prefer asking over misrecognizing; every base-model version starts here. **Stage 2 (50+ interactions)**: plot the similarity-correctness distribution; set thresholds at the valley. **Stage 3 (runtime)**: every recognition writes `threshold_meta` (bucketed by current model); per-entry error rate > 30% → auto down-weight or forced arbitration; on model swap → new bucket restarts at stage 1 plus a lightweight pre-sweep for fast calibration; every adjustment leaves a trail.
